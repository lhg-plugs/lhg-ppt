# lhg-ppt-review：设计自检流程

> 目标：汇报前把"翻车点"全部提前暴露。90% 的 PPT 翻车不是内容不行，
> 是最后一排看不清、错别字在标题上、数据口径前后打架。
> 核心纪律：**先跑脚本（机器），再做走查（人）；blocker 不清零，不许说"可汇报"**。

## 1. 何时使用

- `/lhg-ppt:ppt` 的 Phase 4 → 全程按本 skill 执行
- `/lhg-ppt:ppt-audit` → 对已有 pptx 做体检
- 汇报前 1 小时 → 只跑第 2 步 + 第 5 步（快速版，10 分钟）

## 2. 第一步：跑确定性审计脚本（必做，零成本）

用你所在平台执行本地脚本的方式运行：

```
python3 <插件目录>/scripts/audit/pptx_audit.py --target <pptx文件> --format text
```

- 脚本用 zipfile+XML 直接解析 pptx（**零第三方依赖**，不用装 python-pptx 也能跑）。
- 检查项：字号下限、单页文字量、总页数、对齐、对比度启发式、版权字体提示、演讲者备注。
- 有 blocker 时脚本以非零 exit code 退出——这是设计，不是 bug。
- `--fail-on` 控制 exit code 语义：默认 `blocker`。
- 脚本只做"机器可判定"的事：字号、数量、对齐偏差。它判定不了"这页丑不丑""逻辑通不通"，
  那是第 5 步的事。

## 3. 第二步：分级

| 级别 | 定义 | 处理 |
|---|---|---|
| blocker | 汇报会翻车：正文字号 <12pt、文字是图片不可选 | 必须修（改生成脚本重跑），不修不许汇报 |
| warning | 大概率被吐槽：字号偏小、单页字太多、对齐不齐、对比度低、疑似版权字体 | 本次修掉；修不掉写理由进报告 |
| nit | 洁癖项：缺演讲者备注、页数过少 | 顺手修 |

## 4. 第三步：自动修复 blocker

1. blocker 的修复方式是**改 `build_<主题>.py` 重跑**，不要手工改 pptx（手工改下次重跑就丢）。
2. 修一条跑一遍脚本确认消失。
3. 修不掉的（如用户坚持要用某商用字体）：列进报告的"需人工确认"区，
   **不许**为了清零而改脚本规则或阈值。

### 修复顺序
1. **可读性先修**：字号、对比度——看不清一切白搭。
2. **再修规范**：对齐、文字量、页数。
3. **最后修版权**：字体提示逐条确认（换免费字体或确认有授权）。
4. **修完回归**：只跑审计脚本确认 blocker 消失，不用每次都全量走查（汇报前终检除外）。

### 修不掉的 blocker 怎么写进报告
```markdown
## 需人工确认
- [PPT-FNT-003] 第 3、7 页用了"方正兰亭黑"——公司 VI 字体，已确认有商用授权（附件：授权截图）
- [PPT-TXT-001] 第 12 页附录 210 字——附录页，汇报时跳过，不拆
```
写清"规则ID + 位置 + 事实 + 结论"，不要只写"已豁免"三个字。

## 5. 第四步：人工走查（脚本覆盖不到的）

### 投影测试
- [ ] 接投影/投屏实测一遍：最后一排能看清正文吗
- [ ] 深色底的页面在投影上还看得清吗（投影会吃对比度）

### 内容测试
- [ ] 标题错别字：全文通读，标题零容忍
- [ ] 数据口径：各页同一指标的数字、时间范围一致吗
- [ ] 页标题连读：连起来是一篇通顺的短文吗（见 lhg-ppt-outline）
- [ ] [待补充] 清零了吗：汇报版里不许留

### 合规测试
- [ ] 字体：按 lhg-ppt-aesthetics 第 6 节过一遍版权清单
- [ ] 图片：每张图都有合法来源吗（自制/免费图库/已购买）
- [ ] 涉密：有没有不该出现在 PPT 里的内部数据

### 汇报前 1 小时快速版（10 分钟）
1. 跑脚本：`pptx_audit.py --target <文件>.pptx`，blocker 清零（2 分钟）
2. 标题通读：每页标题读一遍，错别字重点看标题（3 分钟）
3. 数据抽查：随机抽 3 页，数字和口径对得上吗（3 分钟）
4. 投影实测：接上投影翻一遍，最后一排视角看 3 页（2 分钟）
做完这 4 步再出门，翻车概率降 80%。

## 6. 第五步：输出自检报告

报告模板：

```markdown
# PPT 自检报告：<主题>（日期）
## 结论：可汇报 / 需修改
## blocker（n）：已修 n，剩余 n
- [规则ID] 第x页 —— 说明 —— 状态（已修/需人工确认）
## warning（n）：已修 n，豁免 n（理由）
## nit（n）
## 人工走查：投影 x/x 通过，内容 x/x 通过，合规 x/x 通过
## 需人工确认
- ...
```

报告存为 `output/<主题>-audit-YYYYMMDD.md`，下次改稿对照回归。

## 7. 常见误区（反模式）

- ❌ 只跑脚本不做走查——脚本查不出"这页逻辑不通"
- ❌ 手工改 pptx 修 blocker——下次重跑生成脚本就丢了
- ❌ 为了清零改脚本阈值——这是作弊，不是自检
- ❌ "字小点没事，讲的时候我念出来"——听众不听你念，看的是屏幕
- ❌ 汇报前 5 分钟还在改——改完必须重跑脚本+快速走查，否则不如不改

## 8. 误报处理

1. **判断三问**：这页真的有问题吗？规则本意是什么？按规则改会破坏设计吗？
2. **确认误报**：记入报告的豁免清单，写清理由（如"封面艺术字 54pt 被判标题过大"——
   本规则不查标题过大，这只是举例格式）。
3. **拿不准**：按 warning 处理，不要直接忽略。
4. **规则本身有问题**：附最小复现（哪页、什么内容）提 issue（见第 9 节），不要自己改阈值。

### 误报实例（帮你看懂"判断三问"）
- 审计报"第 5 页缺备注"，但第 5 页是纯过渡页（只有一句话标题）→ 豁免，理由"过渡页无需备注"
- 审计报"第 8 页文字 200 字"，但那页是附录（备用问答页）→ 豁免，理由"附录页不计入正文"
- 审计报"疑似版权字体：微软雅黑"，但用户确认公司已购买授权 → 豁免，理由"已有授权（附件：授权截图）"

## 9. 自检与反馈

每次执行完本 skill：

1. 脚本是否真的跑了？→ 没跑不算做。
2. blocker 是否清零或全部列入"需人工确认"？→ 有遗漏就补。
3. 人工走查三组清单是否逐项打勾？→ 打勾要有依据（投影实测/通读记录）。
4. 修复是否走的生成脚本重跑？→ 手工改 pptx 的不算数。

标准冒烟用例：对插件自带的 `fixtures/` 跑脚本，
确认坏 fixture（bad.pptx）的 blocker 全命中、好 fixture（good.pptx）零 blocker
（见仓库根 `smoke_test.py`）。

反馈渠道：以 `[QC] <一句话问题>` 为标题提交到 https://github.com/lhg-plugs/lhg-ppt/issues，
正文写清"输入 → 错误输出 → 期望输出"。规则误报/漏报请附最小复现（页内容描述）。
